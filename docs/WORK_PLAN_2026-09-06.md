## 완료한 작업

### P1 — IME 조합 경로 (`2c235f3`)

**증상:** 여러줄 붙여넣기 오류, 텍스트가 잘려 보임, 스크롤 최하단 점프,
엔터 시 중간부터 잘림.

**진단:** 합성 입력(Playwright `keyboard.type()`)으로는 **3건 모두 재현되지 않았다.**
CDP `Input.imeSetComposition` 으로 실제 한글 조합을 넣자 즉시 재현됐다.

- `resizeOneLineTextarea` 가 조합 중인 줄의 높이 재계산을 **버리고** 있었다.
  붙여넣기는 조합을 취소시키지만 `compositionend` 를 발생시키지 않아
  `composingLineRef` 가 영구히 stale 이 되고, 그 줄은 다시는 높이가 갱신되지 않았다.
  (실측: 5줄 내용에 `clientH: 29`, `scrollH: 107` → 78px 잘림)
- `handleKeyDown` 이 `isComposing` 이면 맨 앞에서 `return` 해 `preventDefault()` 가
  호출되지 않았다. textarea 기본 동작으로 `\n` 이 본문에 박히고 줄 분할은 일어나지 않았다.

**수정:**
- 건너뛴 재계산을 `pendingResizeRef` 큐에 쌓고 조합 해제 시 실행
- 붙여넣기·Enter 에서도 `endComposition()` 으로 조합 상태를 명시적으로 해제
- Enter 분할은 React 상태 대신 **DOM 값(`ta.value`)** 을 기준으로 삼아 글자 유실 방지

**회귀 테스트:** `e2e/ime-composition.spec.ts` — 이 저장소에서 한글 조합 경로가
자동 검증되는 것은 처음이다.

### P0 — 아이콘·단축키 (`565ffb0`)

- 아이콘: ✅(완료) ❌(취소) 👀(진행중) 추가 / `✓ ✔ ✗` `☆ ★` `†` 제거
- `-`/`+` 뒤 공백 → `• ` 자동 변환 제거 (**두 군데**에 있었다:
  `handleLineChange` 와 `handleKeyDown`)
- `---` + Enter → 그 칸에 구분선. 칸은 비운 채 계속 편집 가능, 새 줄 만들지 않음

### 구분선 레이아웃 (`42dafff`, `542a248`)

**증상:** 텍스트가 있는 줄에 구분선을 달면 글자가 세로로 쌓이고 구분선이 위에 걸쳐 보임.

**진단:** `.editor-line` 은 `flex-wrap: nowrap` 인 가로 행이고
`.editor-line-divider` 는 편집 영역의 형제 flex 아이템이다. 구분선이 `width: 100%` 를
요구하면 같은 행에 눌러 앉아 편집 영역을 **폭 20px** 로 짓눌렀다. (기대 359px+)

**수정:**
- `.editor-line` → `flex-wrap: wrap`, 구분선 → `flex: 0 0 calc(100% - 16px)`
  (좌우 margin 8px×2 를 빼지 않으면 8px 가로 스크롤이 생긴다)
- Enter 가 구분선을 새 줄로 옮기던 `prevHadDivider` 동작 제거 —
  구분선이 원래 칸에 남아야 "구분선 아래 칸" 이 성립하고 Backspace 로 지울 수 있다

**교훈:** P0 의 `---` 테스트는 `inputValue()` 만 봐서 이걸 놓쳤다.
**폭이 20px 로 무너져도 textarea 의 value 는 멀쩡하다.**
`e2e/divider.spec.ts` 는 `getBoundingClientRect()` 로 레이아웃을 직접 검증한다.

### P3 — 섹션 (범위 · 색상 · 순서 변경)

계획대로 범위 → 색상 → 순서 변경 순서로 묶어 두 커밋에 나눠 진행했다.

**1) 섹션 범위 (`49c74a3`)** — `LineFormatting.sectionScope?: 'until-next' | 'self-only'` 추가.
미지정(undefined)은 기존 문서 호환을 위해 `'until-next'` 로 취급. 타이틀 좌측에
범위 아이콘(사슬 고리 ↔ 단독 블록)을 두어 클릭으로 전환. `self-only` 로 바꾸면
접기 버튼이 사라지고(`computeSectionHiddenIndices` 가 `sectionScope !== 'self-only'`
일 때만 하위 줄을 숨김), 기존 접힘 상태도 해제한다.

**2) 섹션 색상 (`49c74a3`)** — `LineFormatting.sectionColor?: HighlightColor` 로
기존 하이라이트 7색 팔레트를 그대로 재사용(추천안 그대로 채택). 더보기 모달의
"텍스트 유형" 아래에 같은 스와치 UI를 재사용해 섹션 타이틀 배경색을 고른다.
미지정 시 기존 파란 톤이 기본값이라 과거 문서는 그대로 보인다.

**3) 섹션 드래그 재정렬 (`f779f42`)** — 계획대로 hover 손잡이(⋮⋮, `.editor-section-drag-handle`)
에서만 pointerdown 이 시작되고 `e.stopPropagation()` 으로 텍스트 선택 드래그(줄 안
pointerdown 기반)와 완전히 격리했다. 이동 단위는 `computeSectionBlockRange` 가
`sectionScope` 로 정의한 블록(until-next = 타이틀+하위 줄 전체, self-only = 그 줄만).
드롭 위치는 렌더된 `.editor-line` 요소들의 `getBoundingClientRect()` 를 DOM 순서대로
읽어 계산하므로, 접힌 섹션(하위 줄 미렌더)이나 표 줄이 섞여 있어도 안전하다.
자기 자신의 범위 안으로 놓으면 `moveSectionBlock` 이 원본을 그대로 반환해 이동하지 않는다.

**고스트 프리뷰:** 계획에서 언급한 "펼친 상태 이동 시 고스트 프리뷰"는 전체 블록을
복제 렌더링하는 대신, 커서를 따라다니는 칩(제목 텍스트 + "N줄" 배지)과 드롭 위치의
파란 삽입선으로 단순화했다 — 여러 줄을 통째로 미리보기 렌더링하는 것보다 구현 비용이
훨씬 낮으면서도 "무엇을 어디로 옮기는지"는 충분히 전달된다.

**회귀 테스트:** `e2e/section-scope-color.spec.ts` (범위·색상), `e2e/section-drag-reorder.spec.ts`
(재정렬 — 아래로 끌기, 위로 끌기, self-only 단일 줄 이동, 자기 범위 안 드롭 시 무시).
기존 `e2e/drag-selection.spec.ts` (텍스트 선택 드래그)도 함께 돌려 충돌이 없음을 확인했다.

### P3 재설계 — 섹션 범위를 들여쓰기 기반으로 전환 (`b4b3962`)

**계기:** 위 `sectionScope` 토글 방식을 실사용해보고, 사용자가 더 자연스러운 대안을
제안 — 섹션 추가 시 하단 칸은 기본으로 1단 들여써지고, Shift+Tab 으로 타이틀
레벨까지 내어쓰면 그 줄부터 섹션에서 빠지는 방식(정확히 P3 최초 계획에서
"대안"으로 검토했다가 마이그레이션 위험 때문에 보류했던 들여쓰기 기반 규칙).

**최종 규칙:** 타이틀보다 들여쓰기가 깊은 줄이 연속되는 동안만 그 섹션에 속한다.
**다음 섹션 타이틀을 만나면 들여쓰기와 무관하게 항상 끊김 — 중첩 섹션은 허용하지
않는다** (사용자 확인 사항). `sectionScope` 필드와 좌측 범위 아이콘은 완전히
제거했다.

**우려했던 예외 케이스와 처리 (모두 사용자 확인 후 반영):**
- **기존 문서 마이그레이션** — `normalizeEditorLines` 가 로드할 때마다 구버전
  섹션(본문 들여쓰기 0)을 새 규칙에 맞게 자동으로 +1 들여쓰기 하도록 만들었다.
  이미 새 규칙을 만족하면 손대지 않아 멱등 — DB 스키마 마이그레이션 없이
  기존 정규화 파이프라인에 자연스럽게 얹었다.
- **붙여넣기/가져오기 중간 삽입** — 섹션 본문 중간에 여러 줄을 붙여넣으면
  (특히 `autoMarkdownPaste` 켰을 때) 새로 들어온 줄이 들여쓰기 0으로 들어와
  그 지점에서 섹션이 조용히 끊기는 문제가 있었다. `insertImportedLines` 에서
  삽입 지점이 기존 섹션 안(`findEnclosingSectionTitleIndex`)이면 새로 들어온
  줄들의 들여쓰기를 타이틀 기준으로 자동 보정한다.
- **Tab/Shift+Tab 이중 역할·시각 신호 부재** — 범용 들여쓰기 단축키를 섹션
  이탈 신호로도 쓰게 되지만, 우선순위상 시각적 소속 표시(왼쪽 색선 등)는
  이번 범위에 넣지 않았다. 필요성이 드러나면 추후 별도로 다룬다.
- **MAX_INDENT(6단계) 한계·중첩 미허용**은 계획대로.

**섹션 색상 UI 변경 (사용자 요청):** 더보기 모달 안 스와치 대신, 섹션 타이틀 행에
공간을 거의 차지하지 않는 작은 원형 아이콘을 두고 클릭하면 드롭다운으로 7색을
고르게 했다 (`.editor-section-color-btn` + `.editor-section-color-popover`).
`onPickSectionColor` 가 선택/포커스 범위 대신 클릭한 그 줄에만 직접 적용되도록
콜백 시그니처도 `(index, color)` 로 바꿨다.

**부수 정리:** `computeSectionBlockRange`/`computeSectionHiddenIndices` 등을
`src/renderer/src/edit/sectionFold.ts` → `src/shared/sectionFold.ts` 로 옮겼다
(main 프로세스에서도 재사용 가능하도록 — 당장은 렌더러만 사용).

**회귀 테스트:** `e2e/section-scope-color.spec.ts`·`e2e/section-drag-reorder.spec.ts`
전면 재작성, `src/shared/sectionFold.test.ts`(구 위치에서 이동), 마이그레이션
케이스는 `editorNormalize.test.ts` 에 추가.

### P4 — 창 상단 컬러 랜덤 배정 (`3d94bf3`)

**버그 재현 (착수 전 요청대로 먼저 확인):** `MemoRepository.createMemo()` 가
`활성(미삭제) 메모 개수 % 3` 으로 색을 골랐다. sql.js 로 직접 재현 스크립트를
돌려보니, 메모 하나를 만들고 바로 소프트 삭제하는 걸 반복하면 활성 개수가
항상 1에 머물러 매번 `green` 만 나왔다 — 사용자가 보고한 "결과적으로 초록색만
노출"과 정확히 일치. 활성 개수는 생성 총량이 아니라 현재 시점 스냅샷이라,
"만들고 바로 지우는" 흔한 워크플로에서 특정 색에 고착되는 게 근본 원인이었다.

**수정:**
- `src/shared/memoColors.ts` — 12색 고정 팔레트(`coral`/`green`/`blue` 기존
  3색 그대로 유지 + `purple`/`pink`/`yellow`/`teal`/`indigo`/`orange`/`mint`/
  `gray`/`rose` 9색 추가) + `pickRandomMemoColor(usedColors)`. 기존 3색을
  그대로 팔레트 멤버로 남겨서 과거 메모의 `color` 값은 마이그레이션 없이
  그대로 유효하다.
- 색 배정 방식을 요청대로 변경: **현재 열린 창들이 안 쓰는 색 중 랜덤**,
  전부(12색) 소진되면 팔레트 전체에서 랜덤. `MemoRepository.createMemo()`
  는 색을 인자로만 받고(로테이션 로직 제거), `DataService.createMemoWithStack()`
  이 `WindowManager.listOpenEditWindows()` 로 열린 창들의 색을 모아 넘긴다.
- 설정의 색 슬롯 1~3 사용자 커스터마이징(폴디드 슬롯 왼쪽 색, `SettingsWindow.tsx`
  "모양" 섹션)은 **완전 제거**(사용자 확인) — 12색이 코드에 고정된 팔레트로
  자동 배정되므로 "슬롯" 개념 자체가 더 이상 맞지 않는다.
- `edit.css`: 색상마다 아이콘·본문 배경 규칙이 통째로 반복돼 있던 걸
  `[class*='edit-root--memo-']` 로 한 번만 정의하도록 정리 — 실제로 색상별로
  다른 값(상단 바 배경)만 12색 + default 로 나열. 안 쓰이던
  `src/shared/memoChrome.ts`(edit.css와 색상 매핑을 중복 정의한 죽은 코드,
  어디서도 import 안 됨)도 이 김에 삭제.

**회귀 테스트:** `e2e/memo-color-assignment.spec.ts` — "만들고 바로 닫는 걸
반복해도 매번 같은 색으로 고착되지 않는다"(버그 재현판), "동시에 여러 창을
열면 서로 다른 색을 우선 배정한다". `src/shared/memoColors.test.ts` 에
`pickRandomMemoColor` 단위 테스트(미사용 색 우선, 전부 소진 시 폴백, 예전
버그 패턴 재현).

## 남은 작업

### P5 — 클로드 블록 (기능정의서 v1.0, `3f01822`)

범위 확정: **작성·관리·복사만** (API 연동 없음, 명세 2번 항목 그대로). `/클로드` 로
편집창에 블록을 삽입하고, `{라벨}` 슬롯 구조로 프롬프트를 쓰고, 상태 배지를
수동으로 옮기고, `[복사]` 로 클립보드에 조립해 내보낸다.

#### 기획서 대비 확인된 불일치 — 반영한 결론

1. **Enter/Shift+Enter 표가 실제 섹션 동작과 반대였다 (가장 중요, 사용자 확인 완료).**
   기획서 3-2는 "헤더/슬롯에서 Enter → 하위 들여쓰기 새 줄, Shift+Enter → 상위 레벨
   탈출"이라 되어 있지만, 실제 P2/P3 구현은 정반대다: **Enter는 칸 안 줄바꿈만**
   (새 줄 생성 안 함), **Shift+Enter가 다음 칸(자동 들여쓰기)을 만든다.** 클로드
   블록은 기획서 문구가 아니라 **실제 동작을 그대로 따른다** — Shift+Enter로 슬롯/
   내용 줄을 만든다. 이미 "타이틀에서 Shift+Enter 시 자동 +1 들여쓰기" 로직이
   있으므로, 이 자동 들여쓰기 조건을 `sectionTitle` 뿐 아니라 `claudeBlock`·
   `claudeSlot` 보유 줄에서도 걸리게만 확장하면 된다.
2. **`collapsed` 필드 위치.** 기획서 7번 스키마는 `claudeBlock.collapsed` 로
   중첩시켰지만, 기존 `computeSectionHiddenIndices` 는 최상위 `formatting.sectionCollapsed`
   를 직접 읽는다. 코드 재사용을 극대화하기 위해 **`sectionCollapsed` 필드를 그대로
   공유**하고(3-4의 "기존 sectionCollapsed 방식 재사용"이라는 문구와도 더 합치),
   `claudeBlock` 객체 안에는 넣지 않는다. `claudeBlock = { templateId, status }` 로 축소.
3. **"새 컴포넌트를 만들지 않는다"는 알고리즘·데이터 모델 재사용을 뜻하는 것으로
   해석한다.** 블록 헤더 행(아이콘 + 제목 입력 + 상태 배지 버튼 + `[복사]` +
   접기 화살표)은 시각적으로 기존 어떤 줄과도 다르므로 `EditorLine.tsx` 에 렌더
   분기가 **새로 추가된다.** 다만 그 분기가 쓰는 매커니즘(들여쓰기 기반 소속 판정,
   `sectionCollapsed` 접기, 팝오버 패턴, 이모지 아이콘)은 전부 기존 것 그대로다.

#### 9번 미확정 항목 — 기획서 권고안대로 채택

| # | 항목 | 채택 |

| 1 | 슬롯 라벨 편집 | 잠그지 않음. 슬롯 줄 `text` 변경 시 `claudeSlot` 값을 `{}`·공백 제거해 재파생(동기화) |

  !isBlockHeader` 로 넓혀 클로드 블록과 충돌하지 않게 한다.
- 단위 테스트: `sectionFold.test.ts` 에 `claudeBlock` 헤더 버전의 범위·숨김 계산

- 팝오버에서 템플릿 선택 → 그 줄을 헤더로 변환(`claudeBlock: {templateId, status:'draft'}`,

#### 구현 결과

계획대로 6단계 전부 구현. `isBlockHeader` 일반화 지점이 핵심이었던 만큼,
섹션 e2e(범위·드래그 재정렬·색상) 42개를 전부 재실행해 회귀가 없음을
확인했다. `claudeBlockExport` 는 기획서 6번의 예제 입력을 그대로 단위
테스트에 넣어 출력이 한 글자도 다르지 않게 일치하는 것까지 검증했다.

실제로 만들어보며 확정한 세부 사항 (계획 대비 추가/구체화):
- **템플릿 선택 흐름**: `/클로드` 를 치는 즉시 빈 템플릿(`{첨부}` `{명령}`)으로
  블록을 만들고 포커스를 첫 내용 줄로 옮긴 뒤, 다른 템플릿을 고를 수 있는
  드롭다운을 얹는 방식으로 구현했다. 드롭다운에서 다른 템플릿을 고르면 그
  자리의 슬롯 전체를 새 템플릿 것으로 교체한다 — "선택 전 대기 상태"를 별도로
  관리하지 않아도 돼서 구현이 단순해지고, Esc/바깥 클릭 시 결과(빈 블록 유지)도
  기획서와 동일하다.
- **슬롯 간 이동**: 슬롯은 템플릿이 만들 때 전부 미리 깔리므로, 한 슬롯의 내용
  줄에서 Shift+Enter 하면 그 슬롯 안에 새 내용 줄이 추가될 뿐 다음 슬롯으로
  자동 이동하지는 않는다(스프레드시트처럼 다음 슬롯은 클릭·화살표로 이동).
  기획서에 명시되지 않은 부분이라 가장 자연스러운 해석으로 확정했다.
- **`onCopyClaudeBlock` 등 정의 순서**: `showCopyToastBrief` 를 재사용하는
  콜백은 그 아래에서 정의해야 했다(의존 배열이 선언 전 변수를 참조하면
  런타임 에러) — 사소하지만 실제로 한 번 걸렸던 부분이라 기록.

## 완료한 작업 (추가)

### sticky 타이틀 잘림 (`9ab37a2`)

**증상:** 여러 줄 제목 + 긴 본문을 붙여넣으면 자동 스크롤로 제목이 sticky(한 줄
미리보기) 상태가 된다. 이 상태로 창을 접었다(최소화) 다시 열면 제목이 계속
한 줄로 잘려 보인다.

**진단:** "접기" 버튼은 `WindowManager.ts` 의 `minimizeEditWindow` →
`win.minimize()` 로 **OS 레벨 최소화만** 하고 창을 파괴하지 않는다.
`openEditWindow` 도 기존 창이 있으면 `existing.show()` 만 호출한다 — React
인스턴스가 한 번도 언마운트되지 않으므로 접기 전 `scrollTop` 과 sticky 상태가
그대로 남는다. 스크롤을 최상단으로 되돌리는 로직이 어디에도 없었다.
(참고: 텍스트 데이터 자체는 손실 없음 — 순수 스크롤/렌더링 문제)

**수정:** `EDIT_WINDOW_RESTORED` IPC 채널 추가. `openEditWindow` 가 기존 창을
재사용해 `show()` 할 때 이 이벤트를 보내고, `Editor.tsx` 의 `resetScrollToTop`
(EditorHandle) 이 에디터 스크롤을 0 으로 리셋 — 기존 IntersectionObserver
경로를 그대로 타서 sticky 상태도 자연스럽게 해제된다.

**회귀 테스트:** `e2e/edit-window-restore.spec.ts`

### P2 — 셀(칸) 입력 모델 전환

**요청:** 엑셀처럼 기본 입력 단위가 한 칸. Enter = 칸 안 줄바꿈, Shift+Enter = 다음 칸.
붙여넣기도 한 칸에 통째로.

**결정 사항 (사용자 확인):**
- Enter 동작은 **전면 전환** (설정 토글 없음) — 모든 칸에서 Enter=줄바꿈, Shift+Enter=다음 칸
- `looksLikeMarkdown` 자동 분해는 **옵션으로 유지** — 설정 `autoMarkdownPaste` (기본 꺼짐)
- 마크다운 export 의 칸 안 줄바꿈은 **개행 그대로** — 확인해보니 `formatInlineMarkdown` 이
  이미 문자 오프셋 기준으로 슬라이스만 하므로 `\n` 을 그대로 보존하고 있었다. 추가 작업 불필요.

**구현:**
- `handleKeyDown` 의 Enter 분기를 `!e.shiftKey`(칸 안 줄바꿈) / `e.shiftKey`(칸 분할) 로 분리.
  칸 안 줄바꿈은 `preventDefault()` 하지 않고 textarea 기본 동작에 맡긴다 — 이미
  `handleLineChange` 가 DOM 값을 그대로 반영하고, `handleBeforeLineInput` 이
  `beforeinput`(`insertLineBreak`) 에서 undo 스냅샷을 찍는 경로라 별도 처리가 필요 없었다.
  칸 분할(옛 Enter) 로직은 그대로 Shift+Enter 로 이동 — 리스트 접두 처리·헤딩/체크박스
  carry-over 등 기존 동작 100% 보존.
- **`---` 구분선 매크로는 중간에 사용자 요청으로 Enter 불필요로 변경** — 원래는 plain Enter 로
  트리거했는데, `handleLineChange` 에서 입력값이 정확히 `'---'` 가 되는 순간(세 번째 `-` 입력
  시점) 즉시 발동하도록 옮겼다.
- 붙여넣기(`handleLinePaste`, `appendTextFromClipboard`)의 `looksLikeMarkdown` 분기를
  `autoMarkdownPaste &&` 로 게이팅. 설정은 `Settings.autoMarkdownPaste` (DB
  `auto_markdown_paste`, `SCHEMA_VERSION` 9→10 마이그레이션, 기본값 0/꺼짐) — 설정 창
  "일반" 섹션에 체크박스 추가.

**IME 조합 영향 (P1 재검증):** P1 의 "조합 중 Enter" 특수 처리(`composing && key !== 'Enter'`
는 지나가게 함)는 그대로 뒀다 — 새 모델에서는 plain Enter 가 애초에 "칸 안 줄바꿈"이 목적이라,
조합 중 Enter 가 기본 동작(⁠`\n` 삽입)으로 흘러가는 것 자체가 이제는 올바른 동작이다.
`e2e/ime-composition.spec.ts` 를 조합 중 Enter=줄바꿈 유지 / 조합 중 Shift+Enter=칸 분할
두 테스트로 재작성해 이 뒤바뀐 기대치를 회귀 검증한다.

**영향받은 기존 e2e** (Enter 로 새 줄/칸을 만들던 헬퍼를 Shift+Enter 로 교체):
`ime-composition.spec.ts`, `divider.spec.ts`, `editor-shortcuts.spec.ts`,
`drag-selection.spec.ts`, `edit-window-restore.spec.ts`.

**회귀 테스트:** `e2e/cell-input-model.spec.ts` (신규) — Enter 줄바꿈, Shift+Enter 칸 분할,
붙여넣기 기본 비분해, `autoMarkdownPaste` 켰을 때 분해 복원, `---` 즉시 구분선.

## 아직 손대지 않은 개별 항목

- **복사 시 `[`, `(` 소실** — `memoMarkdownExport.ts` 의 `HEADING_MARKERS` 가
  위계 마커를 **본문 텍스트 안에** 저장한다 (H1=`[]`, H2=`<>`, H3=`()`).
  `stripAllHeadingMarkers` 가 이를 떼어낼 때 헤딩 줄 본문의 괄호가 같이 잘린다.
  근본 해결은 마커를 `formatting` 으로만 표현하는 것 — 데이터 모델 변경 + 마이그레이션 필요.
- **붙여넣기 `await` 후 상태 갱신** — `handleLinePaste` 가 IPC 왕복 뒤에 `setLines`
  를 호출한다. 구조적 위험은 실재하나 재현되는 증상이 없고, 최근 두 커밋
  (`0238791`, `99584e9`) 이 이 rich/plain 클립보드 경로를 안정화한 만큼
  실패 테스트 없이 재작성하면 외부 붙여넣기가 깨질 위험이 더 크다.
- **`scrollTop` 기록자 5명** — `useLayoutEffect` / `scrollLineBottomIntoView` /
  `compositionEnd` / `ResizeObserver` / sticky 가 같은 프레임에 `scrollTop` 을 쓴다.
  경합 구조는 실재하나 증상이 재현되지 않아 리팩터링을 보류했다.

## 개발 환경 메모 (다른 데스크탑에서 이어받을 때)

### e2e 실행

```
npm install
npm run build          # out/main/index.js 가 있어야 e2e 가 돈다
npx playwright test
```

`e2e/helpers.ts` 의 `e2eLaunchEnv()` 가 `ELECTRON_RUN_AS_NODE` 를 제거한다.
VSCode 통합 터미널처럼 Electron 안에서 실행된 셸은 이 변수를 물려주는데,
그대로 상속하면 앱이 순수 Node 로 떠서 `electron.app` 이 undefined 가 되고
**"Process failed to launch!"** 로만 보인다.

### dev 앱 실행

```
unset ELECTRON_RUN_AS_NODE
npm run dev
```

설치된 릴리스 빌드가 실행 중이면 **단일 인스턴스 락에 걸려 exit 0 으로 조용히 종료된다.**
로그만 보면 성공처럼 보이니 프로세스 경로로 확인할 것 —
`node_modules/electron` 이어야 dev, `AppData\Local\Programs\snapnote` 면 설치본이다.

나란히 띄우려면 `SNAPNOTE_E2E=1` (락 우회). 단 이 플래그는 임시 userData 를 쓰므로
기존 메모가 보이지 않는다. 실제 데이터로 테스트하려면 설치본을 먼저 종료해야 한다.

- `core-flows.spec.ts` 3건 (호버 프리뷰 2, 히스토리 1) — 창 포커스·호버 의존.
